# 虚拟支付计费纠正：统一积分与换算

日期：2026-11-10。用户明确纠正：“还是按计分扣款的。这是走的换算”。本文件覆盖此前计划/验收中“独立次数账户、usage 模式、OCR/AI 专用额度”的决定。

## 补充最高优先级：汤圆记账与小管家解耦

用户进一步明确：“汤圆记账 和 小管家要解耦合”。此条覆盖下文对小管家直接增加业务专用 credit_amount 字段的建议；统一积分的业务规则仍然适用。

- 小管家是通用商品/虚拟支付基础设施，负责 App 隔离、商品售价/微信 productId、购买意图、支付订单、验签、查单、通用发货/退款通知及重试。不得理解汤圆账本/积分/上传/OCR/AI/存储。
- 小管家模型、DTO、回调中移除 `target_tenant_id` / `target_user_id`、OCRCount/AICount 以及被解释为记账业务权益的 CreditAmount 等专用字段。不引入对汤圆仓库、数据库、Go 包、域名、路由的硬编码引用。
- 商品保留通用的、不透明的 `delivery_payload`（合法 JSON 对象），小管家只做结构/大小校验、保存与不可变快照、原样交付；不计算、不执行其中的业务规则。管理端以通用“交付配置”维护，不建设动态插件系统。汤圆使用自己的 payload schema（例如 credit_amount、validity_days）解释积分权益，配置示例放汤圆文档；小管家草稿示例使用中性 SKU，不内置汤圆 slug/套餐或默认收款地址。
- 服务间购买意图只交换通用 `business_reference`、商品引用/数量/价格/交付数据快照、付款身份等。账本/业务用户关联只保存在汤圆购买意图表。小管家不能根据客户端提供的账本信息决定到账对象。
- 小管家事件包含稳定 event_id、事件类型、业务订单引用、支付订单标识、商品/金额/数量与不透明交付快照；汤圆适配器验证事件并映射本地购买意图后，再调用积分业务。HMAC/时间窗/幂等等安全约束不变。
- 汤圆核心 BillingService 依赖本地定义的窄 PaymentGateway 接口与本地域类型，不直接依赖 `*xgjclient.Client`、小管家 wire DTO 或 HTTP 路径/签名头。`internal/xgjclient` 只作为基础设施适配器，负责通用 HTTP 契约和消息验真转换；main 装配。不要创建跨仓 Go 依赖或共享数据库。
- 小管家支付开关、IAP/env 等是通用支付能力；汤圆扣费单价、兑换展示、credit_lots 事务、退款回收均属于汤圆。
- 保持简单：保留现有服务间 HTTP 方式，不引入消息中间件、泛化工作流或插件市场。通过边界清晰的接口与 JSON 契约实现解耦。
- 验收增加：用另一个中性小程序/非积分交付 payload 验证小管家可原样保存/签名/投递，不解释业务字段；汤圆核心用 fake PaymentGateway 测试积分逻辑；适配器用契约测试验证跨服务字段/签名/幂等一致。无效积分 payload 在汤圆拒绝，不能让小管家带积分规则。

## 最终业务规则

- 积分是唯一实际计费权益。虚拟道具购买成功后，只向现有 `tenant_credits` / `credit_lots` / `credit_logs` 发放通用积分。
- OCR、AI、上传、存储继续使用原有 `credits_per_upload`、`credits_per_ocr`、`credits_per_llm`、`credits_per_gb_per_day` 扣费配置与原扣费流程。不新建独立 OCR/AI 余额，不提供“积分/次数”计费模式切换，不再插入 UsageGuard。
- 小管家商品后台维护售价（整数分）、微信 productId、上下架状态与通用交付数据。汤圆从交付数据中解析实际到账积分 `credit_amount` 与有效期。积分额是汤圆订单权益快照，改价/改兑换率/改扣费配置不改变已下单权益；小管家只保存、快照、透传 JSON。
- 延续仓库 `docs/billing/credits-pricing.md` 的既有换算建议：默认 100 积分/元；后台可配置实际到账积分（含优惠赠送），不能把价格、积分和“识别次数”当成三套余额。
- OCR/AI 次数仅为可用量估算，来源于同一笔通用积分；OCR 估算必须明确包含上传+识别的完整成本，AI 为单独整理步骤；不能把两种估算显示为可同时兑现的独立配额。例：按代码默认单价 upload=5、OCR=10、AI=20，600 积分约可用于 40 次上传+OCR，或 30 次 AI 整理；全链路 upload+OCR+AI 约 17 次。运行时使用当前平台配置，不硬编码这些示例单价。
- 单价为 0、配置读取失败、负数、溢出/除零要明确处理，估算不可误导为有限配额或计费承诺。

## 开发调整（继续由同一 opencode 会话执行）

1. 保留小管家虚拟支付、商品管理、验签、幂等、outbox、退款通知、权威商品同步、体验登录与终端能力控制。
2. 小管家商品/意图/订单/事件使用通用交付数据快照，汤圆适配器解读后在本地使用 `credit_amount` 快照。清理 OCRCount/AICount 作为实际交付权益的分支；名字/文案允许展示估算但不能作为到账合同。汤圆的 tenant/user ID 不传给小管家。
3. 记账端在同一数据库事务中：校验购买意图与积分快照、锁订单/幂等键、创建现有积分批次、更新现有积分缓存和流水、确认交付。不能先调用独立 Gift 再落幂等标记，防止崩溃或重推多发积分。为购买批次记录订单来源，沿用最近到期优先扣减和 credit_log_details 对账能力。
4. 退款只回收原订单关联的积分批次剩余部分，已有消费进入人工核查；不扣其他赠送/购买积分，不制造负余额。重复/乱序通知仍幂等，退款后晚到发货不再次发放。部分退款继续人工核查。
5. 移除本轮新加的 usage 模型、repo/service、独立次数余额/流水接口、mode 接口和 cron、OCR/AI UsageGuard 及构造参数。不可用 git reset/checkout 恢复整份文件；必须精确保留用户原有未提交的微信登录、内容安全、前端等改动。
6. 这些错误设计尚未上线，不做共享库/生产库数据迁移或清表。删除新代码中的 AutoMigrate 注册即可；如果本机临时库有试验数据，只处理明确属于本任务的临时库，不触碰其他数据库。
7. 汤圆前端改为积分充值/购买、积分余额与原积分流水，订单显示到账积分；需要时显示互斥用途的“约可使用”估算及单价说明。移除模式切换与独立 OCR/AI 次数卡。小管家商品管理使用通用交付配置/定价，种子仍默认草稿；积分套餐配置示例只放在汤圆接入说明。
8. 更新主计划、协议、配置模板、进度、验收和上线说明；旧 review-notes 中次数相关检查标为已被此次纠正覆盖，不能继续作为当前需求。

## 验收

- 先写能证明当前实现错误的失败测试，再修复。
- 虚拟支付成功只增加现有积分；并发/重复通知只发一次；发放和幂等记录同事务；下单后改积分额不影响历史快照；无签名/错账本/错用户不充值。
- OCR/AI 正式路径仍走旧积分 CheckAndDeduct，上传与存储计费保留，unlimited 白名单保留，不存在额外次数扣减。
- 积分批次有效期、余额缓存、流水与扣减明细一致；退款只回收原批次且支持已消费部分审计。
- 用当前配置算出估算次数，单价变化/0/异常/除零有测试。
- 购买发放与退款也要复用原积分操作的锁顺序：先锁 tenant_credits，再操作 credit_lots；调用原惰性过期清理后再计算余额和写流水，不能把到期积分重新计入缓存。退款流水写原批次明细以便对账，与原扣费并发不得死锁/丢余额。退款的“已消费”根据消费明细区分自然到期，不能简单把 Amount-Remaining 全算作已消费。有效期使用本地意图快照并校验交付数据匹配，不信任通知临时改变。
- 演示账号隔离与模拟 OCR/AI 不退化，不能支付/充值/消耗真实积分。
- 两仓 Go 测试（独立临时 MySQL）、uni-app 类型检查/前端能力测试/MP 与 H5 构建、小管家管理端构建通过；gofmt、diff --check 通过。
- 不部署、不真实收款、不读取真实配置密钥、不提交用户旧改动。真实微信联调依旧明确标记未验证。
