# 积分计费策略与成本分析

> 记录时间：2026-07-02
> 触发原因：DeepSeek 上游模型 `deepseek-v4-flash` 涨价，复核现有积分定价是否仍然安全，并给出面向 100 用户规模的正式收费方案。

## 1. 现状：积分消耗与真实成本脱钩

当前 `platform_configs` 里三个动作按固定次数扣积分（`server/internal/model/model.go`），与实际 LLM token 用量无关：

| 动作 | Config Key | 积分 | 真实成本来源 |
|---|---|---|---|
| upload（图片上传） | `credits_per_upload` | 5 | 自建存储，边际成本≈0 |
| ocr（OCR识别） | `credits_per_ocr` | 10 | 自建 rapidocr 服务，边际成本≈0 |
| orc2bill（AI整理，唯一调用 LLM 的动作） | `credits_per_llm` | 20 | **DeepSeek API 调用，真实花钱的一步** |
| 注册赠送 | `credits_new_user_gift` | 1000（一次性） | 获客成本 |

`upload`/`ocr` 走自建服务（rapidocr 容器 + 本地存储），边际成本可以忽略；只有 `orc2bill` 会真实产生 LLM API 费用，是本次分析的核心。

## 2. DeepSeek v4-flash 新价格（2026-07 涨价后）

| 计费项 | 平时价格 | 高峰时段价格 |
|---|---|---|
| 百万 tokens 输入（缓存命中） | 0.02 元 | 0.04 元 |
| 百万 tokens 输入（缓存未命中） | 1 元 | 2 元 |
| 百万 tokens 输出 | 2 元 | 4 元 |

高峰时段定义：每日 9:00–12:00、14:00–18:00（北京时间）。**成本模型统一按高峰价格估算**，作为保守/安全口径。

## 3. 真实用量样本（nana 生产服务器实测）

登录方式：`ssh -p 3312 nana@127.0.0.1`（`Makefile` 的 `nana` target），MySQL：`root/allgood`，库 `fandian`。

`llm_token_usages` 表（token 追踪功能刚上线，目前仅 1 条真实样本，后续应持续积累复核）：

```
tenant_id=12  ref=ocr_record/37  时间=2026-07-02 14:26（高峰时段）
provider=deepseek  model=deepseek-v4-flash
cache_hit=0  cache_miss=1782  completion=1319  total=3101
```

对应 `credit_logs` 记录：该次调用扣了 20 积分（`action=orc2bill`）。

`cache_hit=0` 说明：这类低频记账小工具，两次调用间隔基本超出 DeepSeek 的缓存窗口，**"缓存命中"在实际场景里几乎不会发生**，因此不能按乐观的"缓存命中"场景估算，应以全量未命中的真实样本为基准。

### 单次 orc2bill 真实成本（高峰价口径）

| 项 | tokens | 单价(高峰) | 花费 |
|---|---|---|---|
| 输入-缓存命中 | 0 | 0.04 元/M | 0 |
| 输入-缓存未命中 | 1782 | 2 元/M | 0.003564 元 |
| 输出 | 1319 | 4 元/M | 0.005276 元 |
| **合计** | 3101 | | **≈0.0088 元/次** |

每积分真实成本 = 0.0088 / 20 ≈ **0.00044 元/积分**。

## 4. 100 用户规模的年度成本估算

假设迁移到阿里云 RDS + OSS + ECS：

### 4.1 固定基础设施（100户，年费估算）

| 服务 | 配置建议 | 年费估算 |
|---|---|---|
| ECS | 2核4G（跑 Go server + rapidocr，OCR 有一定 CPU 开销） | 500~800 元 |
| RDS MySQL | 1核1G 入门型（100户数据量很小） | 500~900 元 |
| OSS | 图片存储+流量 | 30~80 元 |
| **小计** | | **≈1400 元/年**（取中位） |

### 4.2 LLM 变量成本（按 0.0088 元/次真实单价）

| 使用强度 | 月均调用/户 | 全年总调用(100户) | 年成本 |
|---|---|---|---|
| 保守（每周1~2次） | 5 | 6,000 | 53 元 |
| 中等（隔天1次） | 15 | 18,000 | 158 元 |
| 活跃（每天1次） | 30 | 36,000 | 317 元 |

### 4.3 获客成本

注册赠送 1000 积分/户，按下文定价（100 积分=1元）折算 ≈1.5 元/户，100户 ≈150 元，一次性，摊入首年。

### 4.4 单户全年成本地板（中等使用假设）

| 成本项 | 户/年 |
|---|---|
| 基础设施分摊 | 14 元 |
| LLM 变量成本 | 1.6 元 |
| 获客成本（首年摊销） | 1.5 元 |
| **合计** | **≈17 元/户/年** |

## 5. 2000 元/100户/年（人均20元）是否可行

| 使用强度 | 总成本(固定+变量+获客) | 毛利 | 毛利率 |
|---|---|---|---|
| 保守 | ≈1450 元 | 550 元 | 27.5% |
| 中等 | ≈1560 元 | 440 元 | 22% |
| 活跃 | ≈1720 元 | 280 元 | 14% |

**结论：勉强覆盖成本，但毛利率 14%~27.5% 太薄。** 未计入：支付渠道手续费、突发流量/备份、人力与迭代运维成本。不建议按此定价上线，风险是活跃度稍一上升利润就被吃光甚至倒贴。

## 6. 正式定价方案

### 6.1 目标

人均年收入 65 元（月均 5.4 元），毛利率 70%~75%。

### 6.2 积分兑换比例

**100 积分 = 1 元**（即 1 积分 ≈ 0.01 元），相对于 LLM 边际成本（0.00044 元/积分）留出约 22 倍安全边际，覆盖基础设施摊销、获客成本、429 限流重试放大、以及其他未建模的运维开销。

> 现状缺口：代码里目前没有积分↔人民币兑换比例的正式配置（只有管理员手动充值 `Gift` 和注册赠送），如需落地建议新增 `platform_configs` key `credits_per_yuan`（默认值 `100`）。

### 6.3 套餐设计

| 套餐 | 价格 | 积分 | 约合识别次数(35分/次=upload+ocr+orc2bill) | 毛利率 |
|---|---|---|---|---|
| 注册赠送（不变） | 免费 | 1,000 | ~28次，约1个月试用额度 | — |
| 月卡 | ¥6.5 | 650 | ~18次/月 | 73.8% |
| 年卡（9折鼓励年付） | ¥58 | 7,800 | ~223次/年，约19次/月 | 70.7% |
| 高频版月卡（天天开票门店） | ¥12 | 1,300 | ~37次/月 | 87%（固定成本摊得更薄，活跃用户更赚） |

### 6.4 风险与后续动作

1. **样本量太少**：目前仅 1 条真实 `llm_token_usages` 记录，需要随用量增长持续复核实际 token 消耗是否与估算一致，尤其关注多笔交易的大账单场景（completion tokens 可能显著更高）。
2. **429 重试放大成本**：`server/pkg/llm/client.go` 的 `generateWithRetry` 遇限流重试最多 3 次，每次都是完整请求，积分只按最终成功扣一次。高峰时段限流概率更高，这块目前定价的安全边际里已预留但未精确建模。
3. **积分兑换比例未落库**：需要决定是否将 `100积分=1元` 写成正式 config 供后台调整，而不是仅停留在文档里的约定数字。
